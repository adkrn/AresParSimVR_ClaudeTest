# Lesson — 비행기 경로 절차 스킵 흐름 안정화

## Context
훈련 시뮬레이터의 절차 스킵(`StateManager_New.ExecuteSkip`)에 누적된 8개 버그를 한 사이클에 추적·수정. 사용자 보고는 "스킵 기능 문제 많아" 1줄이었지만 정적 분석 + 6개 케이스 라이브 검증으로 root cause 매트릭스 확정.

---

## 패턴 1: 멀티씬 환경에서 `SceneManager.GetActiveScene()` 함정

### 증상
`MissionBrief → StandDoor` 직접 스킵(idx 0→11) 시 **씬 전환이 일어나지 않고 UI만 떴다 → NullReference**.

### 원인
`IsSceneChangeRequired`가 active scene 이름으로 Lobby 여부를 판단했음:
```csharp
if (SceneManager.GetActiveScene().name != lobbySceneName) return false;
```
근데 이 프로젝트는 **AppBootstrap이 항상 active scene**이고 Lobby/Main이 **additive로 로드**되는 구조. 그래서 active scene은 영원히 `AppBootstrap` → 항상 false 반환 → 씬 전환 분기 도달 못함.

지금까지 작동하던 케이스(target ≤ TakeOff index)는 **자연 진행 path가 씬 전환을 처리**했기 때문에 노출 안 됐음. target이 TakeOff 이상으로 직접 점프하는 케이스에서만 폭발.

### Reuse Rule
- **멀티씬 로딩 환경에서 active scene 비교는 신뢰 불가**. `SceneManager.sceneCount` + `GetSceneAt(i).name` 으로 **로드된 씬 목록 검사**가 안전.
- 진단 시 `currentScene` 과 비교 대상 둘 다 로깅 (`len=N` 까지) — 보이지 않는 char/공백도 잡음.

### How to apply
씬 이름 비교 로직이 들어간 모든 코드(`LoadLobbyIfNeeded`, `IsSceneChangeRequired`, `LoadSceneWithCleanup` 등)에서 active scene 가정 재확인. 새 씬 추가 또는 부트스트랩 도입 시 회귀 검증 필수.

## 패턴 2: 절차 경계를 넘는 stale 콜백/코루틴

### 증상 3건 (모두 같은 root cause)
1. **AirPlane MoveTo 핸들러 잔존**: 이전 절차의 `MoveTo to Route#N` 람다 핸들러가 큐에 남아 비행기 자연 도달 시 **다음 절차의 OnProcedureComplete를 잘못 호출** → InAir이 land 전 자동 완료.
2. **PlayCharacter.Stand() 의 TempDelayAni**: `Stand()` 가 1초 후 `OnSuccessAction`을 호출하는 코루틴 시작. 스킵 중 `ExecuteEssentialActions`에서 호출되면 코루틴 잔존 → 후속 절차(GoJump) 진입 직후 stale OnSuccessAction → GoJump 즉시 완료, 5초 카운트다운 무시.
3. **TempJumpDelay 5초 timeout**: GoJump이 외부 신호로 일찍 끝나도 코루틴 살아있음 → FreeFall 진행 중 timeout 발화 → `_character.Jump()` 재호출 → FreeFall 자세 충돌.

### Reuse Rule
**모든 시간 지연/명령 큐가 절차 경계를 넘으면 즉시 stale 위험**. 다음 3 패턴 중 하나로 차단:
| 패턴 | 적용 위치 | 코드 |
|---|---|---|
| 코루틴 핸들 저장 + SetProcedure 시 stop | 시간 지연이 있는 절차 entry 메서드 | `_jumpRoutine = StartCoroutine(...)` + `CleanPrevEvents`에서 `StopCoroutine` |
| 명령 큐 + 람다 핸들러 일괄 정리 | 외부 시스템(AirPlane 등) | `ClearCommandQueue()` — `OnEventX = null` 까지 |
| 스킵 전용 변형 호출 | 절차 entry 메서드의 부수효과 분리 | `Stand()`(코루틴 시작) ↔ `SkipStand()`(로그만) |

### How to apply
절차(Procedure) 단위로 코루틴/이벤트 lifecycle 검토. `CleanPrevEvents`가 절차 변경의 단일 진입점 — 새 코루틴/이벤트 추가 시 여기에 cleanup 호출 추가가 의무. `ExecuteEssentialActions`처럼 절차의 essential side-effect만 호출하는 path는 **코루틴/시간 지연 로직 호출 금지** (SkipXxx 변형 사용).

## 패턴 3: 명령 큐의 일관된 lifecycle — `CleanPrevEvents`에 `ClearCommandQueue`

### 핵심
정상 흐름과 빠른 진행(교관이 도달 전 다음 명령) 둘 다 처리하려면 **`SetProcedure` 진입 시 매번** 비행기 명령 큐를 클리어. 정상 흐름엔 큐가 비어있어 no-op, 빠른 진행 시 stale 명령 즉시 차단.

### Reuse Rule
Command queue + 외부 자율 진행(자연 이동) 패턴을 쓰는 모든 시스템에서 **state transition 진입점에 큐 클리어를 default로** 두는 게 안전. opt-in (스킵 시에만 클리어)은 빠른 진행 케이스에서 폭발.

## 패턴 4: `GetProceduresBetween` 같은 collection slice의 주석↔코드 drift

### 증상
주석엔 "(startIdx, endIdx 제외)"라고 양끝 제외라고 적혀 있는데, 실제 코드는 `GetRange(startIdx, count)`로 startIdx 포함. 사용자가 BUG-1 fix 후 `_currentProcedure`(=startIdx)의 essential action(예: Item 강제 착용)이 누락됨을 우연히 발견했지만, **off-by-one 자체가 의도와 안 맞음**.

### Reuse Rule
- collection slice 메서드는 unit test로 boundary 케이스 4개 ((,), [,), (,], [,]) 모두 명시.
- 주석과 코드가 어긋나면 **호출자가 어느 쪽에 의존하는지** 우선 추적 후 fix 방향 결정. 한 쪽으로 통일하면서 호출자 보강 필요.

## 패턴 5: 진단 인프라 우선 (방향 B) — fix 직전 1단계

### 핵심
가설이 2개 이상 갈리는 버그는 **로직 변경 없이 진단 로그만 먼저** 추가. 다음 재현 1회로 가설 확정 → 그제서야 surgical fix.

이번 사례: `IsSceneChangeRequired`에서 `currentScene` / `lobbySceneName` / `mainSceneName` / `mainSceneLoaded` 한 줄 로그 추가 → 사용자 재현 1회로 "active scene이 AppBootstrap" 확정 → fix 정확히 적중.

### Reuse Rule
회귀 위험이 있는 영역에서는 **"진단 로그 PR" → "fix PR"** 2단계 분리. 진단 PR은 회귀 위험 0이라 안심하고 머지 가능. 진단 결과로 fix 방향 좁힘.

## 패턴 6: "주석된 fix는 fix가 아니다"

코드 주석에 "[버그 수정]" 이라 써놓고 본문이 통째로 주석 처리된 패턴 발견. git blame으로 의도 추적 후 영구 삭제. 표면 의도(주석)와 실제 동작(코드)이 갈리는 흔한 패턴.

### Reuse Rule
- 주석 처리된 코드 블록 발견 시 **그대로 두지 말고** git blame → 의도 확인 → 살리거나 삭제. 죽은 채 남으면 다음 작업자가 살아있다고 오해.
